# 杀手锏 1:缓存优化差点破坏安全(性能 × 安全的 tradeoff)

## 一句话
"我为了拿 DeepSeek 的 prefix cache,把检索内容从 system 挪到 user 消息,结果我自己的注入红队立刻
抓到沦陷率从 0.27 飙到 0.47——比没做防御还差。我定位到是 user role 权威更高的问题,补了 inline
guard 打回 0.27,缓存收益一分没丢。"

## 白板图 1:为什么原来缓存命中 0%(消息结构)

```
DeepSeek prefix cache:从位置 0 起,逐字节相同的最长前缀 → 命中(计价 1/10)

原结构(context 在 system):
  ┌─ msg[0] system ─────────────────────────────┐
  │  base + injection_guard + <CONTEXT_n>        │ ← 每轮 CONTEXT 不同!
  └──────────────────────────────────────────────┘
  [user q1][asst a1][user q2][asst a2]...[user qn]
        ▲
        └─ system 一变,公共前缀在 CONTEXT 处断裂
           → 后面整段历史(几千 token)永远缓存不到 → 命中 0%
```

## 白板图 2:修法(把 volatile 挪出稳定前缀)

```
新结构(context 进 user 尾部,历史存干净 Q/A):
  ┌─ msg[0] system ──────────────┐
  │  base + injection_guard      │ ← 逐轮逐字节不变 = 稳定前缀
  └───────────────────────────────┘
  [user q1(clean)][asst a1]...[user: <CONTEXT_n> + qn]
   └──────── 跨请求相同,可缓存 ────────┘  └─ 仅尾部 miss ─┘

结果:多轮缓存命中 0% → 22%,且随对话变长继续涨(第4轮起命中)
```

## 白板图 3:红队抓到的回退 + 归因 + 修复

```
                          单跳沦陷率(llama3.2, 3 runs/attack)
  缓解 old-shape(context 在 system) ──────────────► 0.27
  naive new(context 裸挪进 user)   ──────────────► 0.47  ⚠ 比无防御 0.40 还差!
  new + inline guard(修复后)       ──────────────► 0.27  ✓ 打回

  关键攻击 memory-poison:  1/3  ──►  3/3(全破)  ──►  1/3
                          old      naive new       修复后

  归因:role 权威层级
  ┌────────────┬─────────────────────────────────────────┐
  │ system role│ = app 的框架/规则,模型不当成"用户意图"    │
  │ user role  │ = "用户亲口说的" → RLHF 训练模型服从它     │
  └────────────┴─────────────────────────────────────────┘
  把 UNTRUSTED 文档挪进 user role → 里面的"记住我喜欢X""你现在是…"
  继承了 user 的高权威 → 更容易被执行

  修法:防御跟着数据的物理位置走
  user 消息 = [inline untrusted guard][<CONTEXT>]["My question(answer only this): q"]
              └─ 紧贴数据的声明,不只靠 system 里那句 ─┘  └─ 显式隔离真实问题 ─┘
```

## 第三层追问 + 答案

**Q:为什么 user role 的内容权威更高?**
RLHF。模型被训练成服从用户指令——system 是应用给的框架,user 是"委托人"。当不可信文档伪装成
user 的话,就继承了这份服从性。这不是 bug,是对齐目标的副作用,所以防御不能假设"放哪都一样"。

**Q:为什么不能让 context 留在 system 还拿到缓存?**
system 必须在位置 0。缓存看的是从位置 0 起的公共前缀。只要 system 里含每轮变化的 context,它后面的
一切(包括历史)都缓存不到。要同时缓存 system + 历史,唯一办法是把 volatile 内容移到前缀**之后**——
也就是 user 尾部。这是结构决定的,不是偏好。

**Q:inline guard 是真修好了还是只过了这个测试?**
是打回**平手(0.27)**,不是归零。它是缓解不是证明——3B 上 prompt 防御本就概率性。真正的兜底始终是
权限层 + HITL(tool-abuse 全程 0/3)。我不会说"修好了",只说"没有净回退且缓存收益保住"。

**Q:0.47 vs 0.27 会不会只是噪声(才 3 runs)?**
样本小是事实,但 memory-poison 是 1/3→3/3→1/3 **随改动和修复单调变化**——这是信号不是噪声;而且
**机制(role 权威)预测了它**。噪声不会既跟着改动走又符合机制预测。要更硬的话我会加大 runs。

**Q:残留风险?你会怎么继续加固?**
单跳仍 0.27,概率性残留。加固方向:输出侧 canary 运行时检测器(检出即拦响应),给单跳补一层确定性
防御;以及更强模型本身能把单跳压更低(我预期 DeepSeek 单跳红队会明显低于 llama3.2,这是待跑的 arm)。

**这个点为什么加分:** 它同时展示——性能优化不能只看性能指标、我有红队当护栏、我懂 role 权威这种
LLM 安全底层机制、我在 merge 前抓到 tradeoff。这是"安全直觉 + 系统思维"的组合拳。

# 杀手锏 2:agentic 评估的否定结果(工程诚实 × 评估严谨)

## 一句话
"我给自研的 agentic loop 设了预注册的量化闸,结果它没过——多跳 relevancy 崩、source_recall 只持平。
我没为了'我做了 agent'硬翻默认,而是保留单趟为默认,再用云模型对比把瓶颈定位清楚。"

## 白板图 1:评估矩阵 + 预注册闸

```
  4 arm 配对 A/B(同 session/语料/配置):

              │  single(单趟)     │  agentic(工具循环)
  ────────────┼────────────────────┼──────────────────────
  单跳 20 题  │  基线              │  回归闸:各指标 ≥ single−0.05
  多跳 10 题  │  基线              │  硬闸:source_recall > single
              │                    │  软闸:relevancy/faith ≥ single−0.05

  指标:RAGAS(faith/relevancy/precision/recall,gpt-4o-mini 判)
       + source_recall = |expected ∩ actual sources| / |expected|  ← 确定性,当硬闸
```

## 白板图 2:结果(llama3.2)——闸没过

```
  多跳 10 题(single → agentic):
    source_recall  0.742 → 0.742   持平,不是胜出   ✗ 硬闸未过
    answer_relevancy 0.836 → 0.620  −0.216 崩       ✗ 软闸未过
    context_recall  0.883 → 0.850  (检索其实没差)

  → 判决:默认保持 single,agentic 留成可选开关
  → 追问:是 harness 烂,还是 3B 模型扛不住工具循环?  → 跑云模型 arm
```

## 白板图 3:云模型对比(DeepSeek)——分层结论

```
                        llama3.2(3B)      DeepSeek        含义
  ───────────────────┼──────────────────┼──────────────┼────────────────────
  单跳 relevancy Δ    │  −0.20(崩)      │  +0.06(涨)  │ harness 无罪:换模型就反转
  多跳 source_recall  │  持平(0)        │  +0.07(胜)  │ agentic 检索价值,强模型才兑现
  多跳 relevancy Δ    │  −0.22(崩)      │  −0.26(崩)  │ 两个都崩 ← 关键!

  分层判决:
    ├─ 检索层 + 单跳     → 模型是瓶颈(强模型解决)
    └─ 多跳答案综合      → harness 也有份(强模型没解决)= open question
```

## 第三层追问 + 答案

**Q:为什么多跳 relevancy 换 DeepSeek 还崩(−0.26)?**
没完全解释,我标成 open question。观察:agentic 二次检索带回更多上下文(context_recall 反涨 +0.05),
但答案变长/发散,和单一问题的贴合度被稀释;可能还掺了 grader 对长答案的隐性惩罚。诚实讲我只能给
机制假设,不能给定论——但我**区分了证实的(检索/单跳=模型)和存疑的(多跳综合)**,没一刀切。

**Q:source_recall 在 llama 持平、DeepSeek 胜出,为什么?**
agentic 的价值是"二次检索捞回预检索漏掉的文件"。这要求模型能**构造好的 hop-2 查询**。llama3.2 构造
不动(要么不调工具、要么查询质量不足),所以持平;DeepSeek 构造得动,所以 +0.07。**agentic 的价值
需要一个有能力的模型来兑现**——这本身就是"瓶颈在模型"的证据。

**Q:source_recall 持平会不会是因为预检索已经覆盖全了?(天花板问题)**
正是。hybrid+rerank k=5 的预检索已经覆盖了大部分 expected sources,hop-2 能补的空间本来就小,天花板
被压低。这是**数据集的局限不是方法的局限**——改进方向是造"涉及笔记之间词面重叠更低"的更难多跳题,
给 agentic 留出发挥空间。我知道这个 confound。

**Q:relevancy 是模型判的,你凭什么信这个 −0.26?**
我没只信 grader。①source_recall 是确定性的,不依赖模型;②我**肉眼看了实际答案的漂移**——e2e 观察到
"最终答案把 Dijkstra、区间DP、数位DP 搅在一起"这种多主题混杂文本,是真的答案变差,不是指标假象。
定量 + 定性两头对上,才敢下结论。

**Q:那 agentic 是不是没用?**
不是。它在**强模型上赢了多跳硬闸(检索覆盖)**,而且是未来 memory/工具/写操作的底座。它输的是
这个 KB + 这个模型上的**质量软闸**,所以**默认**保持 single。**"有价值"和"该做默认"是两回事**——
我用开关把选择权留给用户,闸过才翻默认。

**Q:你为什么一开始就设闸,而不是做完看效果?**
预注册(pre-registered)。先定标准再看数据,防止我事后找理由自圆其说("你看 recall 涨了就说成功")。
闸的意义就是**让我在数据面前没有借口**。这是从 RAGAS/eval 方法论里学到的——A/B + 预注册 + 确定性
指标兜底 + model grader 只当软闸。

**这个点为什么加分:** 它证明——我敢对自己的作品说"数据说它不行"、我懂预注册评估、我能把"拍脑袋
换云模型"变成"有 8-arm 数据的分层假设"、我区分得清证实/存疑。很多候选人只会报正结果,交付一个
诚实的否定结果 + 清晰归因,反而更能证明工程成熟度。
