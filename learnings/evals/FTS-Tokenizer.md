# 实验记录：FTS5 分词器 —— 让混合检索的关键词腿在中文上真的生效

> 2026-08-02。自查中发现 hybrid 的 BM25 腿在中文上完全失效，修复后用 RAGAS 对照验证。
> 配套：[Stack-Migration-and-RAGAS-Validation.md](../decisions/Stack-Migration-and-RAGAS-Validation.md)（那份里 `context_recall 0.338 → 0.706` 的归因需要本实验修正）。

## 1. 目的（为什么做）

`chunks_fts` 建表时没写 `tokenize=` 子句，用的是 FTS5 默认的 **unicode61**。unicode61 按 Unicode 类别切词，而汉字属于「字母」类别 —— **一串没有空格的中文会被切成一个 token**。

后果：中文查询几乎永远命中不了 BM25，**hybrid 在中文内容上静默退化成纯向量检索**。系统不报任何错。

先做了一轮定性实测确认问题真实存在（同一份中文文档，两种分词器）：

| 查询 | unicode61（现状） | trigram |
|---|:-:|:-:|
| 哈希值 | ❌ miss | ✅ HIT |
| 完整哈希 | ❌ miss | ✅ HIT |
| 最短路径 | ❌ miss | ✅ HIT |
| Dijkstra | ✅ HIT | ✅ HIT |
| SHA | ✅ HIT | ✅ HIT |

**中文全 miss，英文全中。**

### ⭐ 连带发现：一个正面数字需要修正归因

迁移评估里 `context_recall 0.338 → 0.706` 那个提升，是在**中英混排**的 LeetCode 笔记上测的 —— 那批笔记里全是 `Dijkstra`、`DP`、`heapq`、`O(n log n)` 这类英文 token。**FTS5 是靠这些英文起作用的，不是靠中文。**

数字本身没错，但「混合检索让 recall 翻倍」这句话的**适用范围比原来以为的窄**。

## 2. 过程（怎么做）

### 第一版判断是错的：只改建表参数反而更糟

原始估计是「加个 `tokenize='trigram'`，半小时能出对照数字」。**实测证伪。**

因为还有第二个坑：**调用方是把整个用户问题原文丢进 `MATCH` 的**。trigram 下一个长句会被当成一个**连续子串**去匹配 → 整句 MATCH 实测 **0 命中**。只改 tokenizer，长中文问题的关键词腿不但没修好，比原状还差。

所以 tokenizer 和查询构造**必须一起改**，这也是它们最终住在同一个模块里的原因。

### 否决的第三条路：`Intl.Segmenter`

JS 运行时内置的分词器，理论上比 trigram 更「正确」（真分词而不是滑窗）。实测**更差**：

```
爬 / 楼梯 / 问题 / 为什么 / 和 / 斐 / 波 / 那 / 契 / 数列 / 有关
提交 / 的 / 完整 / 哈 / 希 / 值 / 是 / 一个 / SHA / 校 / 验 / 和
```

常用词切对了，**技术术语全崩** —— 「斐波那契」切成 4 个单字、「哈希值」切成 3 个单字。**单字成词会匹配到一切，精度比现状还差。** trigram 虽然笨，但没有未登录词（OOV）问题。

### 实现三块，缺一不可

1. **建表**：`tokenize='trigram'`。
2. **查询侧**：CJK 切 3 字滑窗、拉丁保留整词、每个词条加引号、用 `OR` 连接、上限 32 个词条。
   **加引号顺带堵掉了原来「用户原文直进 MATCH」那个语法注入面** —— `NEAR`、`*`、`-`、引号现在在提取阶段就被丢掉，根本到不了 FTS5 解析器。
3. **迁移重建索引**。最容易漏的一块：schema 用的是 `CREATE VIRTUAL TABLE IF NOT EXISTS`，表已存在时是 **no-op** —— **不写迁移，老用户会永远静默保持旧索引，永远看不到这个修复**。重建从 `chunks` 表灌回，**不需要重新 ingest、不需要重新 embedding**（正文本来就在，倒排索引只是派生物）。

**一个防漂移的设计细节**：查询侧的 tokenizer 是**从活表的 DDL 里读出来的**，不是从环境变量读的（按 db 句柄缓存）。这样查询形状永远不可能和真实索引漂移。

## 3. 结果

RAGAS 检索双指标，28 问，k=5，bge-m3，同语料同 grader。原始数据：`backend/eval_results/fts_tokenizer.json`。

| tokenizer | context_precision | context_recall |
|---|:-:|:-:|
| unicode61（基线） | 0.8702 | 0.8988 |
| **trigram** | 0.8524 | **0.9524** |

- **recall +0.054**，**远超 ±0.02 噪声底** → 真实收益。
- **precision −0.018**，**在噪声内** → 没有可测的代价。

## 4. 读法（学到什么）

1. **语料构成才是这次结果最值得讲的地方**：这份评估语料**只有 8% 是中文**（红楼梦繁体、es6-async、几份自有 learnings 文档），其余 92% 是英文（Rust Book、傲慢与偏见、node-stream、kubectl）。**在一份 92% 英文的语料上仍拿到 +0.054 的 recall，同时英文精度没掉** —— 一次实验同时回答了两个问题：**中文修复有真实收益，且 trigram 没有伤到英文。**
2. **归因是干净的**：两个臂**都**用了新的查询构造（OR + 引号），唯一变量是 tokenizer 和 CJK 词条形状。所以 +0.054 可以归给中文修复本身，不是被查询改造带上去的。
3. **「一个建表参数的事」这个直觉是错的**，而且错的方向是危险的 —— 单独改会让情况变糟。**存储层的参数和查询层的构造是耦合的，动一个必须验另一个。**
4. **`IF NOT EXISTS` 是静默失效的经典形状**：新用户拿到修复，老用户永远拿不到，而且两边都不报错。凡是 schema 有 `IF NOT EXISTS`，就必须问一句「已存在的那批怎么办」。

## 5. 保留的已知限制（过了闸也照说）

- **trigram 匹配不了 2 字查询**（「算法」「排序」「二叉」实测全部 0 命中），而中文技术术语里 2 字词非常多。要治得上真分词，而 `Intl.Segmenter` 实测更差。
- **OR 融合让 BM25 排序变噪**：「红黑树的复杂度」这个查询，把「堆排序」那篇排到了「红黑树」那篇前面 —— 因为「复杂度」的 trigram 也命中了。影响可控：FTS 这条腿只给 RRF 提供一个排名列表，最终顺序由融合和精排决定。

## 6. 决策

- ✅ **trigram 转正为默认**，含迁移重建。环境变量可切回 unicode61 做 A/B（同 `KNOWHIVE_RERANK_STYLE` 的做法）。
- 📝 **迁移评估的归因已修正**：`0.338 → 0.706` 归因于「混合检索」成立，但要补一句「在中英混排语料上，FTS 腿的贡献来自英文 token」。
- 面试叙事：自查发现一条腿是瘸的 → **第一版判断被自己实测证伪**（只改建表参数反而更糟）→ 三块一起改（含最容易漏的迁移）→ 否决一条看起来更「正确」的路（`Intl.Segmenter`）→ RAGAS 过闸 → **主动交代两个没修的限制**。
