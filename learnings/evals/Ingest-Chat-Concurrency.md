# 实验记录：一边导入一边聊天会怎样 —— 以及"瓶颈是 SQLite"这个直觉又错了

> 2026-08-05。装置：`server/spike-concurrency.ts`，原始数据 `backend/eval_results/concurrency.json`。

## 1. 目的（为什么做）

关于并发我一直只有一句假设：**"单用户本地应用，不会有并发。"**

**这句话是错的**，而且不需要多用户就能证伪：**文件监听在外部编辑时会自动重新导入**——
用户在 Obsidian 里改了一批笔记，导入就在他正在聊天的时候开始了，**没有人主动选择过它**。

导入和聊天共用两样东西：**一个 SQLite 句柄**和**一个 Ollama 实例**。
所以有两条互不相同的失败路径，而且**修法完全不同**：

| 猜想 | 表现 | 修法方向 |
|---|---|---|
| SQLite 写竞争 | `SQLITE_BUSY` 或读延迟飙升 | 连接池 / 分库 / 排队 |
| Ollama 排队 | **纯延迟，一个错都不报** | 限流 / 优先级 / 分离 embedding 实例 |

## 2. 过程（怎么做）

- **臂 A**：空载，连发 N 次聊天，记 TTFT 和总时长。
- **臂 B**：先起一个 30 个文件的导入任务（复制自 `eval-corpus/md` 的大文件，
  改名保证每个都是真新活 —— 哈希相同会被跳过），**然后立刻发同样的聊天**。
- 同问题、同顺序，唯一变量是有没有负载。
- 判定不只看 HTTP 状态：**流中途的 error frame 也是 200**，所以要扫流内容。
- 第二轮开 `KNOWHIVE_TIMING=1` 复跑，把 retrieve 拆成 embed / search / rerank 归因。

```bash
bun run server/src/index.ts --port 18291 --data-dir <dir>
bun run server/spike-concurrency.ts --port 18291 --corpus <dir of .md> --chats 5 --copies 30
```

## 3. 结果

**总体（n=5/臂，llama3.2 + cross-encoder 精排）**

| 臂 | 失败 | 中位 TTFT | 中位总时长 | 最大总时长 |
|---|---:|---:|---:|---:|
| 空载 | **0/5** | 1559ms | 3110ms | 8187ms |
| 导入中 | **0/5** | 3563ms | 7218ms | 9186ms |

> TTFT **2.29x**、总时长 **2.32x**、**失败 0**。
> 复跑（n=4）：TTFT 1.57x、总时长 1.92x、失败 0。**量级一致。**

**⭐ 归因：退化不在我以为的地方**

| 阶段 | 空载 | 导入中 | 结论 |
|---|---|---|---|
| `search`（SQLite 读） | 15–25ms | **7–22ms** | **完全没变** |
| `rerank`（进程内 ONNX，吃 CPU） | 1407–2458ms | 1445–1772ms | 基本没变 |
| **推断的 LLM 生成段** | ~1.6s | **~4.5s** | **≈3x，退化全在这里** |

- **`SQLITE_BUSY` / `database is locked`：两轮日志里 0 次。**
- 一个 error frame 都没有，没有断流，导入照常推进（臂 B 结束时 7–10/30）。

## 4. 读法（学到什么）

1. **"瓶颈是数据库"这个直觉又错了 —— 这是同一个项目里第二次。**
   第一次是延迟瀑布：以为"检索慢"，实测 hybrid 检索只占 5ms、精排占 46%。
   这次是以为"写锁卡读"，实测 SQLite 读完全不受影响。
   **两次都是我把最'像'瓶颈的那个组件当成了瓶颈。**
2. **为什么 SQLite 没事，说得出机制**：`db.ts` 建库时执行了
   `PRAGMA journal_mode = WAL`。**WAL 下写不阻塞读** —— 写进单独的日志文件，
   读的还是主库快照。这不是运气，是一个当时随手做对的选择。
3. **真瓶颈是 Ollama**：导入的每个分片都要 embedding，走的是同一个 Ollama 实例，
   和聊天的 embedding + 生成抢同一个 runner。**这类竞争一个错都不报**，
   只表现为延迟 —— 而这正是最难在日志里发现的那种问题。
4. **退化 2.3x 但零失败，这个组合本身是结论**：说明**没有正确性问题，只有体验问题**。
   两者的严重度和修法优先级完全不同。

## 5. 诚实边界

- **n=5、单机、一次运行。** 这是量级证据不是统计估计。两轮分别 2.29x / 1.57x，
  **说明方差不小**，真实值大概在 1.5–2.5x 之间。
- **负载是 md 批量导入，不是 PDF。** PDF 走独立插件进程（实测 501 页 70 秒、峰值 3GB），
  **那条路会额外抢内存和 CPU，可能比这更糟。仓库里没有大 PDF，我没测。**
- **只测了本地 Ollama 这条路。** 云端 provider 下 LLM 不在本机跑，
  **这个竞争大概率消失** —— 也就是说这个问题是"本地优先"这个选择的自带代价。
- **导入没跑完**（臂 B 结束时 7–10/30）。我测的是"导入进行中"的稳态，
  不是完整导入周期的平均。

## 6. 决策

- ✅ **不改架构。** 零失败 + WAL 已经把最危险的那条路堵上了。
- 📝 **该做但没做**：导入进行时在 UI 上给个提示（"正在重新索引，回答可能变慢"）。
  **2.3x 的延迟如果没有解释，用户会以为是应用坏了。** 成本极低，优先级不高。
- 📝 **想清楚了但不做**：给 embedding 单开一个 Ollama 实例能消除竞争，
  **但要求用户跑两个 Ollama —— 和"双击就能用"的产品形态冲突**。
  多租户/云端部署下这个取舍会反过来。
- 📌 **面试用**：这条最值钱的不是数字，是**"我的直觉又指错了地方，而我有装置能证伪它"**。
