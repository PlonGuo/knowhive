# 实验记录：agentic 到底贵多少 —— 一个平均值会骗人的指标

> 2026-08-05。[Agentic-vs-SingleShot](Agentic-vs-SingleShot.md) 的补充：那份有质量闸和延迟，
> **唯独没有成本**。装置：`server/spike-cost.ts`，原始数据 `backend/eval_results/cost_single_vs_agentic.json`。

## 1. 目的（为什么做）

agentic 的评估结论是「质量闸过了、体验闸没过」，体验闸的证据只有延迟（多跳中位 12.4s → 19.7s）。
**「agentic 更贵」一直是个断言，没有数字。**

而这个数字现在几乎白捡：修掉 `includeUsage` 之后两条 provider 路径都上报 token 了
（见 [FTS 之外的那条 usage 修复](../career/09-工程改进实战记录.md)），Langfuse 也注册了模型价格。

## 2. 过程（怎么做）

- 6 个问题 × {single, agentic}，**同语料同检索配置**，唯一变量是 `chat_mode`。
- 问题一半单跳、一半跨两篇文档 —— **跨文档的那几题才是 agent 有理由调工具的地方**，
  也才可能出现成本差。
- **精排必须走 cross-encoder，不能走 LLM 精排**：后者会多一次 `generateText`，
  那笔 token 会被算进总数并错误地归因给 `chat_mode`。
- usage 直接从 `/chat` 的流里读，**不从 Langfuse 读** —— 这样数字能独立成立，
  trace 变成交叉验证而不是唯一来源。
- 模型 `deepseek-v4-pro`（$0.435 / $0.87 per 1M in/out）。本地 llama3.2 记 0：
  **本地推理没有按 token 计费的账单**，但电费和时间不是零。

复现：

```bash
bun run server/src/index.ts --port 18290 --data-dir <dir>   # deepseek + cross-encoder
bun run server/spike-cost.ts --port 18290 --out backend/eval_results/cost_single_vs_agentic.json
```

## 3. 结果

**总体（n=6/臂）**

| 臂 | 平均 input | 平均 output | 平均总 token | 平均成本 | 中位延迟 | 真的调了工具 |
|---|---:|---:|---:|---:|---:|---:|
| single | 1432 | 362 | 1794 | **$0.000937** | 8623ms | 0/6 |
| agentic | 13698 | 726 | 14424 | **$0.006590** | 15551ms | **3/6** |

> token **8.04x**，成本 **7.03x**，延迟 **1.80x**。

**⭐ 但这个平均值两头都不像 —— 成本是双峰的**

| | n | 总 token | 成本 | 中位延迟 |
|---|---:|---|---|---|
| **agentic 没调工具** | 3 | 2371 → 3287（**1.4x**） | $0.001194 → $0.001604（**1.3x**） | 8063 → 6598ms |
| **agentic 调了工具** | 3 | 1216 → 25561（**21.0x**） | $0.000681 → $0.011576（**17.0x**） | 9183 → 23632ms |

**逐题最极端的一条：62.5x。**

| 问题 | single | agentic | 工具调用 | 成本倍数 |
|---|---:|---:|---:|---:|
| Rust 所有权三条规则 | 2145 | 2883 | 0 | 1.2x |
| Send trait / Rc | 615 | 2766 | 1 | 3.1x |
| async/await vs promise 链 | 3030 | 4138 | 0 | 1.4x |
| 跨两章比较数据移动 | 2696 | 47356 | 5 | **14.9x** |
| agentic 结论 × 延迟瀑布 | 338 | 26560 | 5 | **62.5x** |
| 精排 vs 混合检索谁更贵 | 1937 | 2839 | 0 | 1.4x |

## 4. 读法（学到什么）

1. **「agentic 贵 7 倍」这句话不该说。** 正确的说法是：
   **不调工具时基本白送（1.3x，多的只是更长的系统提示词和工具定义）；
   一旦开始多跳，就是 17x 起，最坏 62x。**
   一个双峰分布报平均值，等于两个峰都没描述对。
2. **成本的驱动因素不是「模式」，是「跳数」。** 每多一跳，上一跳检索到的整段
   context 会连同历史再进一次 prompt——**输入 token 是按跳数累乘而不是累加的**。
   47356 这个数就是 5 次工具调用把 context 反复重放的结果。
3. **最贵的那题（62.5x）恰好是 single 最便宜的那题**（338 token）。
   机制上说得通：single 因为检索没捞到东西所以 context 很短；
   agentic 恰恰因为第一次没捞到，所以才反复搜。
   **agent 在最该省的地方最费。**
4. **和已有结论一致但更狠**：原来的体验闸只看到延迟 1.8x，
   **成本这条闸的失败幅度大一个数量级**。这加强了原来的决策
   （默认不翻 `single`），而不是推翻它。

## 5. 诚实边界

- **n=6，单次运行，没有重复采样。** 这是量级证据（1.3x vs 17x 的差距远超噪声），
  **不是精确估计**。要给出置信区间得跑多轮。
- **只测了 `deepseek-v4-pro` 一家。** 工具调用倾向是模型行为，换模型跳数分布会变——
  llama3.2 在原评估里 20 题只有 2 题真调了工具，**它的双峰会更极端地偏向便宜那一侧**。
- **缓存折扣没算。** 我用的是扁平价目，命中缓存的 input 仍按全价——
  **系统性高估**，而 agentic 因为反复重放相同 context，理论上缓存命中率更高，
  **也就是说真实差距应该比 17x 小一些**。这条对我的结论不利，所以必须说。
- **问题是我自己出的**，且我刻意挑了一半跨文档的题去逼工具调用。
  **调工具的比例（3/6）不代表真实使用分布。**

## 6. 决策

- ✅ 默认保持 `single` —— 理由从「质量闸没过 + 延迟 1.8x」补强为
  **「+ 多跳时成本 17x」**。
- 📝 **UI 该做的事**：agentic 的 ⚡ 按钮旁边应该显示上一次的 token/成本。
  **用户在按下之前有权知道这一下大概值多少钱。** 未做，已记。
- 📝 **值得一试的优化**：多跳时把上一跳的 context 换成摘要而不是原文重放。
  这直接打在第 2 条那个机制上。**要用同一套装置量化后再决定。**
